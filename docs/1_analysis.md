# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ОБҐРУНТУВАННЯ ТЕХНОЛОГІЧНОГО СТЕКУ

## 1.2. Інженерний конкурентний аналіз систем відеоаналітики

У межах дослідження проведено системний архітектурний скаутинг трьох індустріальних аналогів, що вирішують завдання спортивної телеметрії.

**Hudl Sportscode (Хмарна платформа)**
- Архітектурний патерн: Розподілений хмарний моноліт.
- Протоколи передачі даних: REST API для метаданих, HTTP/2 для відео, WebSockets.
- Стек даних: AWS RDS (PostgreSQL), Amazon S3, Redis.
- Technical Bottlenecks: Висока мережева затримка (Latency) при спробі обробки відео у реальному часі через повну залежність від хмарних серверів. Вимагає стабільного широкосмугового інтернет-з'єднання.

**Veo Analytics (Пакетна обробка на базі IoT)**
- Архітектурний патерн: Batch-Processing Pipeline (пакетна обробка після завершення запису).
- Протоколи передачі даних: MQTT (IoT-моніторинг), REST API.
- Стек даних: MongoDB, AWS S3.
- Technical Bottlenecks: Відсутність Real-Time аналітики. Висока вартість хмарного інференсу відео високої роздільної здатності обмежує горизонтальне масштабування.

**Catapult MatchTracker (Злиття телеметрії)**
- Архітектурний патерн: Event-Driven Architecture.
- Протоколи передачі даних: UDP (для натільних сенсорів), gRPC, GraphQL.
- Стек даних: InfluxDB, PostgreSQL, Apache Kafka.
- Technical Bottlenecks: Апаратна надлишковість (обов'язкові натільні сенсори). Проблема просторово-часової синхронізації (Time Sync) оптичних кадрів та сенсорної телеметрії спричиняє джитер (jitter).

### Порівняльна інженерна матриця систем відеоаналітики
| Інженерний критерій | Мій проєкт (F2-diploma) | Hudl Sportscode | Veo Analytics | Catapult MatchTracker |
| :--- | :--- | :--- | :--- | :--- |
| **Архітектурний патерн** | Edge Computing, Clean Architecture, EDA | Розподілений хмарний моноліт | Batch-Processing Pipeline | Event-Driven Architecture |
| **Протоколи обміну (API)** | WebSockets (Real-time), REST API | REST, HTTP/2, WebSockets | REST API, MQTT | gRPC, UDP, GraphQL |
| **Стек даних (СУБД)** | MongoDB (Event Data), SQLite (профілі) | AWS RDS (PostgreSQL), Redis | MongoDB, AWS S3 | InfluxDB, PostgreSQL, Kafka |
| **Швидкодія (Latency)** | Ultra-low (Локальний Edge-інференс) | High (повна залежність від хмарної мережі) | Non-real-time (асинхронна обробка) | Low (але наявний джитер синхронізації) |
| **Інфраструктура** | Docker, GitHub Actions, Edge Node | AWS Cloud Infrastructure | AWS Cloud + Пропрієтарні камери | Cloud Infrastructure + Натільні IoT-сенсори |

### Аналітичний висновок підрозділу 1.2
Проведений інженерний аналіз існуючих рішень виявив критичні архітектурні обмеження, що перешкоджають їхньому використанню для оперативної підтримки рішень в умовах обмеженої мережевої інфраструктури. Хмарно-орієнтовані монолітні системи та платформи пакетної обробки демонструють високу мережеву затримку (latency) та залежність від зовнішніх обчислювальних потужностей. Альтернативні подієво-керовані системи вимагають розгортання дороговартісної апаратної інфраструктури, що створює проблеми із просторово-часовою синхронізацією даних.

Для усунення виявлених недоліків у межах кваліфікаційної роботи обрано парадигму Edge Computing із застосуванням патернів Clean Architecture та Decoupled Telemetry. Використання локального інференсу моделей комп'ютерного зору (YOLOv8) та великих мовних моделей (LLM) дозволяє ізолювати обчислювальний контур від зовнішніх мереж, забезпечуючи обробку відеопотоку в реальному часі (Ultra-low latency). Застосування WebSockets для доставки агрегованих метрик гарантує високу пропускну здатність системи.

Наведені архітектурні переваги власного технологічного стеку над аналогами обумовлюють доцільність переходу до етапу системного проєктування.
